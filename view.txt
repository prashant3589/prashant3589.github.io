How Microsoft Entra ID Sites.Selected permissions work
Your current design follows Microsoft's least-privilege access model for SharePoint Online. The key point to explain to your IT team is:
Giving your Entra ID application the Microsoft Graph Sites.Selected application permission does not automatically give it access to any SharePoint site. A separate site-level permission grant is required to authorize the application for a specific site and role, such as write.

1. Your current setup: two levels of permission
Level 1 — Microsoft Entra ID
Application authentication and permission scope
•	Client ID identifies your application.
•	Client secret allows the application to authenticate.
•	Microsoft Graph Sites.Selected (Application permission) authorizes the app to request access to specifically assigned SharePoint sites.
•	Admin consent is required for the application permission.
Separate site-level grant required
Level 2 — SharePoint site
Resource-specific authorization
•	IT grants your application's Client ID access to the specified SharePoint site.
•	The grant specifies a role, such as write.
•	Your application can then perform operations allowed by that role on that site.
Microsoft's official documentation describes both the Entra consent and the explicit SharePoint resource assignment as necessary parts of the Selected-permissions model.

What the different values mean
Value	Purpose
Client ID / Application ID	Identifies the app whose access is being granted. This is the ID IT normally uses in the site permission assignment.
Client secret	Credential used by the app to authenticate and obtain an access token. It does not grant SharePoint access by itself.
Tenant ID	Identifies the Microsoft Entra tenant in which the application authenticates.
Object ID	Context matters: the app registration's object ID and the enterprise application's/service principal object ID are different from the Client ID. For a SharePoint site permission grant, IT should use the application's Client ID in the application.id field.
SharePoint Site ID	Identifies the SharePoint site collection receiving the permission assignment.
Role = write	Defines the application's access level on that particular site.
Microsoft Graph distinguishes the application's identity from its credentials and from the resource-level role assigned to it.

2. What access does Sites.Selected actually provide?
Think of Sites.Selected as a permission to be considered for access to selected sites, rather than permission to access every site.
Configuration	Result
Sites.Selected added, but admin consent not granted	Application permission is not fully configured.
Admin consent granted, but no site grant exists	The app has no access to SharePoint sites through this Selected permission.
Site grant exists with read	The app can read the granted site's content and metadata, within the role's scope.
Site grant exists with write	The app can read and modify content and metadata on the granted site, subject to the role and API operation.
A different SharePoint site has not been granted	Sites.Selected does not automatically authorize the app to access that other site.
Site grant is removed	Access through that particular grant is removed.
These outcomes follow Microsoft's official Selected permissions overview.

3. What does the write role allow?
For your requirement—uploading documents from Azure Blob Storage to a SharePoint document library—the write role is the relevant site-level role to discuss with IT.
Site-level role	Meaning
read	Read resource metadata and contents.
write	Read and modify resource metadata and contents.
owner	Owner-level role for the assigned resource.
fullcontrol	Full control over the assigned resource.
Microsoft lists these roles in its Selected permissions documentation. 
 
Microsoft Learn
Important distinction: write is not the same as fullcontrol. For a document-upload integration, request only the access required by the workflow. If your integration only uploads files to one document library, ask IT whether a more narrowly scoped permission such as Lists.SelectedOperations.Selected is suitable for that library. Sites.Selected grants access at the site level, whereas the newer Selected permissions can target lists, files, or folders.

4. How the application authenticates when the pipeline runs
Your application uses the client credentials flow. There is no signed-in user in this flow; the application acts as itself.
1. Azure Data Factory / application code
Starts the upload operation
2. Microsoft Entra ID
Authenticates the app using its client ID and secret; issues a Microsoft Graph access token
3. Microsoft Graph
Receives the token and the requested SharePoint operation
4. SharePoint Online
Checks the app's site-level assignment and whether its role permits the requested operation
The app needs both a valid token carrying the required application permission and the explicit SharePoint site assignment. Possessing the client secret or knowing the site ID is not sufficient by itself.

5. What exactly should IT configure?
IT should create a site-level permission assignment for your application. Conceptually, the Microsoft Graph request is:
POST https://graph.microsoft.com/v1.0/sites/{siteId}/permissions
Content-Type: application/json
Request body:
{
  "roles": ["write"],
  "grantedToIdentities": [
    {
      "application": {
        "id": "<YOUR-APPLICATION-CLIENT-ID>",
        "displayName": "<YOUR-APPLICATION-NAME>"
      }
    }
  ]
}
This is the documented Microsoft Graph API for granting an application a role on a specific SharePoint site.

6. How to validate that the setup is correct
Once IT confirms the assignment, test these items:
1.	Entra ID: Confirm Sites.Selected is configured under Microsoft Graph Application permissions and admin consent has been granted.
2.	Site assignment: Ask IT to confirm that the correct Client ID has the write role on the intended SharePoint Site ID.
3.	Token: Acquire a token for Microsoft Graph using the client credentials flow. The token should represent the application, not a user.
4.	Read test: Call a suitable Graph endpoint to verify access to the intended site.
5.	Upload test: Upload a small test document to the target document library and confirm it appears in SharePoint.
6.	Negative test: If your security team permits it, verify that the application cannot access another site for which it has not been granted access.
If the upload fails, check the token, tenant, site ID, application permission consent, site assignment, destination library path, and the Graph API response. A successful token request alone does not prove that SharePoint access has been granted.
